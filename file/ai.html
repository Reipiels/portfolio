1.AI 협업 수행 체계

개별 프로젝트 수행에 앞서, AI 도구의 운용 방식과 협업 규칙을 다음과 같이 수립·적용하였음.

1.1작업 성격별 AI 도구 분담 운용

  • 기획·1차 설계는 Claude(웹), 교차 검증은 GPT·Gemini, 코드 구현·서버 작업은 Claude Code로 분담 운용함
  • 동일 질의를 복수 AI에 교차 투입하여 답변이 갈리는 지점을 검증 대상으로 식별함
  • 정적 HTML 퍼블리싱 등 단순 작업에는 고비용 도구를 투입하지 않는 선택 기준을 적용함
단계도구
기획 · 1차 설계Claude (웹)
교차 검증GPT · Gemini
코드 구현 · 서버 작업Claude Code
정적 HTML 퍼블리싱Claude (웹)

1.2프로젝트별 AI 온보딩 문서(CLAUDE.md) 운영

  • 패키지 구조, 에러 처리 패턴, 커밋 컨벤션, DB 네이밍 규칙을 프로젝트별 문서로 명문화함
  • 신규 AI 세션 시작 시 해당 문서를 우선 참조하도록 하여, 세션 교체와 무관하게 일관된 작업 기준을 유지함

1.3동시 세션 간 작업 경계 및 문서 소유권 분리

  • 모사방지솔루션 개발 시 알고리즘 담당(엔진 세션)과 화면·인프라 담당(서비스 세션)을 분리 운영함
  • 코드 경로별 소유권을 표로 정리하고, 일괄 커밋(git add -A)을 금지하는 대신 경로 지정 부분 커밋만 허용하는 규칙을 수립함

1.4공유 문서 유실 사고 및 재발방지 절차 수립

  • 두 세션이 공동 편집하는 의사결정 기록 문서에서 문단이 유실되는 사고가 발생, git 이력으로 원인을 추적함
  • "표는 추가만 한다(기존 결정은 신규 항목으로 대체)", "편집 직전 파일 재확인", "커밋 후 삭제 라인 diff 직접 확인"의 3원칙을 수립하였고 이후 재발 없음

1.5자동화 적용 범위에 대한 판단 기준 적용

  • 자동 댓글 등록기능 개발 시, 네이버 공감/댓글 자동 클릭이 표면상 성공으로 처리되나 실제 상태는 변경되지 않음을 실측으로 확인함
  • 우회 시도를 지속하는 대신, 국내 매크로 클릭 관련 형사 판례(형법 제314조)를 검토한 후 "AI 초안 생성 + 담당자 최종 승인·게시" 구조로 설계를 변경함
  • 동일 요청이 재차 접수될 경우 해당 리스크를 우선 고지하도록 프로젝트 문서에 지침으로 명기함

1.6자동화 도구 개발 중단 결정 사례

  • 복수 사내 서버의 SSL 인증서 갱신 봇 개발에 착수하였으나, 갱신 시마다 AI에 직접 작업을 지시하는 방식이 도구 개발·유지보수 대비 효율적임을 확인함
  • 이에 따라 봇 개발을 중단하고 AI 직접 수행 방식으로 운영 방침을 확정함 — 자동화 도구화 여부 자체를 비용 대비 효과로 판단한 사례

1.7레거시 코드베이스 대상 AI 작업 규칙 체계(AGENTS.md) 설계

  • Java 7·Spring 3.1.1·ES5 기반 레거시 시스템(uniwiseWeb, uniwiseWebAdmin)은 AI가 최신 문법으로 코드를 생성할 경우 빌드가 실패하는 제약이 있음
  • 루트 문서에 불변 제약(Java 8+ 문법 금지, ES6+ 문법 금지 등)을 명기하고, 하위 모듈(java/myBatis/views)별 세부 규칙 문서로 위임하는 "중앙 통제 + 위임" 구조를 설계·적용함
  • 실제 운영 장애(로컬 WAS 기동 중 빌드 정리 명령 실행으로 사이트 전체 404 발생)를 계기로 위험 명령의 사전 확인 규칙을 추가함
  • 10년간 운영 중인 핵심 매출 로직은 AI의 개선 제안과 무관하게 수정 금지 영역으로 명시함

1.8반복 장애 원인의 단계적 규명

  • Windows 빌드 반복 실패 문제를 4개 프로젝트(uniai·unimosa·uninsight·curvefit)에서 각각 접함
  • 1차 추정(동시 세션 충돌) → 실패 패턴 관찰로 기각 → 2차 규명(폴더 읽기전용 속성) → 3차 규명(해당 속성을 부여한 주체가 Google Drive 백업 동기화임을 확정)의 순서로 원인을 단계적으로 좁힘

1.9수행 과정에서 정립한 운영 원칙

  • 수립한 가설은 실측으로 재검증하고, 반증 시 철회 사실과 사유를 문서에 남김
  • AI가 처리하기 편한 방식과 실무자가 사용하기 편한 방식이 다를 경우 후자를 채택함
  • 법적·정책 리스크는 사전 조사 후 문서화하여 후속 판단의 제약 조건으로 명기함
  • 완전 자동화와 완전 수동의 양자택일 대신, 양측을 실제 구현·비교한 후 절충안을 채택함
  • 원인 미확정 시 "미확정"으로 기재하고, 차후 확정이 가능하도록 진단 체계(로깅·모니터링)를 우선 구축함
