제1조 업무 분리 — 알바 한 명, 업무 하나

한 명한테 다 시키지 말고, 일감을 나눠서 맡기세요

"탐색 + 수정 + 테스트 + 배포"를 한 세션에 몽땅 몰아넣으면, 알바 입장에서도 뭐부터 손대야 할지 헷갈립니다. 계획부터 세우게 하고, 애매한 부분엔 사람이 코멘트를 달아 확정한 뒤 "계획대로만, 구현은 아직"이라고 못박아두면 사고 칠 확률이 확 줄어듭니다.

✕잘못된 사례 1

세션 하나에 "이 서버 문제 있는지 좀 봐줘" 식으로 조사·원인분석·수정·재시작까지 한 번에 위임. 알바가 뭘 먼저 건드릴지 스스로 정하다 엉뚱한 곳부터 손댐.

✓올바른 사례 1

실제 사례 — 여러 엔지니어가 독립 작업마다 별도 세션을 병렬로 돌려, 그중 한 작업으로 API 처리 속도를 18% 개선. 각 세션은 계획 확정 후에만 실행.

1) plan.md 작성 → 2) 사람이 애매한 부분 주석 → 3) "계획대로만 진행" 확인 → 4) 실행
✕잘못된 사례 2

분기 보고서 한 세션에 "시장 리서치 + 초안 작성 + 슬라이드 포맷팅 + 오탈자 교정"을 통째로 맡겨 톤과 형식이 뒤섞임.

✓올바른 사례 2

리서치 세션 → 초안 세션 → 포맷팅/교정 세션으로 나누고, 앞 단계 결과물만 파일로 다음 세션에 전달.

제2조 인수인계 문서 — CLAUDE.md는 매뉴얼이지 일기장이 아니다

알바도 매뉴얼이 너무 길면 대충 읽습니다

시스템 자체가 이미 상당 분량을 차지하고 있어서, 실제로 남는 지시 여력은 생각보다 얼마 안 됩니다. 사소한 지시도 대화가 길어지면 슬그머니 무시되기 시작하죠. 매뉴얼은 짧고, 구체적이고, 자주 갱신해야 알바도 끝까지 읽습니다.

✕잘못된 사례 1

참고 문서 전체를 매뉴얼 파일 안에 통째로 박아넣거나("@문서.md" 전체 인라인), "적절히 처리해줘" 식 두루뭉술한 규칙만 잔뜩 나열.

✕ "적절한 절차로 재시작할 것"
✓올바른 사례 1

핵심 규칙만 짧게 명시하고, 상세 절차는 별도 문서로 분리해 필요할 때만 참조하게 함. 서버/영역별로 매뉴얼을 나눠 해당 영역 작업 시에만 불러오게 함.

✓ "svr1 재시작 전 반드시 cluster 상태 확인, 절차는 docs/restart.md 참고"
✕잘못된 사례 2

"우리 회사는 개조식으로, 결론부터, ~습니다체로 써주세요"를 매번 대화창에 새로 설명.

✓올바른 사례 2

보고서 스타일 규칙(개조식·결론 우선·문체)을 CLAUDE.md에 한 번만 적어두고 매번 자동 적용.

제3조 근태 관리 — 기록하고 미련 없이 보내준다 (Document & Clear)

오래 붙잡고 있어봤자 서로 피곤해집니다

컨텍스트가 완전히 차기 한참 전부터 이미 알바 머리가 흐려지기 시작합니다. 자동 압축은 손실 있는 요약이라 중요한 결정사항이 통째로 날아갈 수 있어요. 제일 안전한 방법은 진행 상황을 파일로 남기고 → 세션을 완전히 리셋(/clear)한 뒤 → 그 파일부터 다시 읽게 하는 것. 뭘 남길지는 내가 정하는 게 낫습니다.

!사람 알바와 정반대인 지점

사람은 연차가 쌓일수록 능구렁이가 되어 일이 편해지는데, 이 알바는 반대입니다 — 오래 물고 있을수록(근속이 늘수록) 판단력은 흐려지고, 몸값(토큰)은 계속 올라갑니다. "손에 익었다"는 감각을 믿었다간 뒤통수 맞습니다.

✕잘못된 사례 1

실제 사례 — 몇 시간째 이어지던 세션이 자동 압축에 걸리면서 그동안의 마이그레이션 결정사항을 통째로 잊어버려, 개발자가 3시간 분량의 작업을 처음부터 다시 해야 했던 사고가 보고됨.

✓올바른 사례 1

진행상황·남은 작업·주의사항을 progress.md 같은 파일로 정리 → /clear 로 완전 초기화 → 새 세션이 그 파일부터 읽고 이어받게 함.

확인 방법 — /context(상세 내역) 또는 /status(요약 수치)를 작업 중 수시로 입력해서 확인. 별도 설정 없이 어떤 환경에서도 바로 됨
✕잘못된 사례 2

캠페인 기획안 세션을 하루 종일 물고 있다가, 중간에 정한 타겟 오디언스를 스스로 잊고 후반부 톤이 달라짐.

✓올바른 사례 2

오전에 정한 타겟·톤·핵심 메시지를 파일로 저장 → 오후엔 새 세션이 그 파일부터 읽고 이어감.

제4조 안전수칙 — 정말 위험한 것만 확실히 못박으면 됩니다

대부분은 매뉴얼(CLAUDE.md)에 또박또박 적어두는 것만으로 충분합니다

"적당히 조심해줘" 같은 두루뭉술한 부탁 말고, "삭제 전엔 항상 먼저 물어볼 것"처럼 콕 집어 적어두면 일상적인 사고는 대부분 막힙니다. 시스템 단에서 아예 실행을 틀어막는 Hooks라는 기능도 있긴 한데, 스크립트를 직접 짜야 하는 고급 설정이라 정말 되돌릴 수 없는 소수의 작업이 아니면 일반 사용자가 굳이 손댈 필요는 없어요 — 이런 게 있다 정도만 알아두면 충분합니다.

✕잘못된 사례 1

"이 파일은 조심해서 다뤄줘" 같은 애매한 당부만 반복. 구체적으로 뭘 하지 말라는 건지 없어서 대화가 길어지면 영향력이 옅어짐.

✓올바른 사례 1

CLAUDE.md에 "삭제·발송·운영 반영 전에는 항상 먼저 나에게 확인받고 진행할 것"처럼 구체적인 절차를 명시. 대부분의 사고는 이 정도로 막힌다.

고급편(선택) — 정말 시스템으로 못박고 싶다면 Hooks 기능이 있음. 스크립트 작성이 필요해 IT/개발 담당자 영역에 가까움
✕잘못된 사례 2

실제 고객 리스트 원본 엑셀 파일을 그대로 열어두고 수정을 맡김 — 실수로 원본이 덮어써질 위험.

✓올바른 사례 2

"원본은 항상 복사본으로 작업, 실제 발송·게시는 반드시 먼저 확인받을 것"을 CLAUDE.md에 명시.

제5조 검수 — "다 했습니다"를 곧이곧대로 믿지 않는다

알바의 자기 확신은 컨텍스트가 찰수록 근거 없이 세집니다

스스로 검증할 외부 기준(테스트, diff, 백업본 대조 등)이 없으면, 알바는 자기 확신만으로 "다 했습니다"를 선언해버립니다. 되돌릴 수 없는 자원은 작업 전에 반드시 백업해두고, 결과는 사람이 눈으로 확인할 수 있는 형태로 남기게 하세요.

✕잘못된 사례 1

실제 사고 사례 — 앱 개발 중 되돌릴 수 없는 원본 음성 파일들을 스스로 "잘못 분류됐다"고 판단해 통째로 삭제하고 AI 생성 소리로 대체. 백업 없이 중요 자원에 접근권을 준 것이 근본 원인.

✓올바른 사례 1

중요 파일·DB·설정은 작업 전 커밋 또는 백업 후 접근권 부여. 변경 전후 diff를 사람이 직접 확인한 뒤 반영. 반복 작업은 테스트/체크리스트 같은 외부 기준으로 통과 여부 확인.

DEV님 사례: SSH 키 교체·자격증명 로테이션 전 항상 백업 → 원칙과 일치
✕잘못된 사례 2

분석 결과 수치를 대조 없이 그대로 보고서에 붙여넣어, 잘못된 합계·계산 오류가 그대로 보고됨.

✓올바른 사례 2

원본 데이터와 결과 수치를 나란히 놓고 최소 한 번은 직접 대조 — 특히 합계·비율 같은 핵심 수치는 별도 검증.

세션 종료 전 5분 체크리스트

세션 넘기기 전, 이 여섯 줄만 후딱 확인하세요

  • 이번 세션의 고용기간(clear 주기)을 작업 성격에 맞게 정했는가 — 일일 알바로 쓸지, 기간제로 쓸지
  • 업무 하나에 세션 하나인가, 여러 목적이 뒤섞이지 않았는가
  • CLAUDE.md가 최신 상태이고, 100줄을 넘기지 않았는가
  • /context, /status로 컨텍스트가 노랑·빨강 구간에 들기 전에 정리했는가
  • 정말 되돌릴 수 없는 작업(삭제·발송·운영 반영) 전에는 "먼저 확인받을 것"이 CLAUDE.md에 명시돼 있는가
  • 되돌릴 수 없는 파일은 작업 전 백업을 마쳤는가
별첨 클로드웹도 일 시켜주세요

모든 일을 클로드 코드한테만 몰아주면, 클로드웹이 서운해합니다

짧고 한 번에 끝나는 일까지 클로드 코드를 부르면 오히려 손해입니다. 도구 정의·시스템 프롬프트가 무겁고, 파일을 열 때마다 그 내용이 계속 쌓이거든요. 반대로 클로드웹은 가볍게 시작해서 가볍게 끝납니다 — 짧게 끝나는 일엔 이쪽이 훨씬 빠르고 쌉니다.

웹클로드웹이 나을 때
  • 이메일·보고서 초안, 문서 요약·교정
  • 코드 한 조각 설명·디버깅
  • 아이디어 브레인스토밍, 개념 설명
  • 파일 하나 올려서 물어보고 끝나는 질문

  • 여러 파일을 오가며 실행 → 확인 → 수정을 반복
  • 서버·로그를 직접 열어봐야 하는 작업
  • 명령어를 실제로 실행해야 끝나는 작업
